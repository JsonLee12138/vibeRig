# Pi 公司模式与 Codex A/B 证据

## 结论

在两个只读需求开发样本中，Pi 单代理、Pi 公司模式和 Codex 的内容质量均达到当前规则上限 40/40。没有证据表明 Pi 公司模式的答案优于 Codex，也没有节约 token。

Pi 公司模式消耗 330,767 个有效 token，Codex 消耗 72,205 个，前者是后者的 4.58 倍；总耗时分别为 319.6 秒和 240.1 秒，前者是后者的 1.33 倍。Pi 单代理仅消耗 64,353 个有效 token，并以 110.6 秒完成。

## 测试口径

- 分支：`codex/pi-company-plane`
- 模型：`gpt-5.6-terra`
- 推理级别：父代理、Pi subagent 和 Codex 均为 `low`
- 权限：只读仓库，不修改文件，不写 Plane
- 样本：跨前后端 OAuth 安全方案、并发批量导入重复写诊断
- Pi 公司模式：后台并行派发，必须通过 `get_subagent_result(wait: true)` 取回并综合全部专家结果
- 有效 token：排除重复缓存前缀读取；Pi 统计父代理与 subagent 的 `input + output + cacheWrite`，Codex 统计非缓存输入与输出

## 汇总

| 运行方式 | 内容质量 | 路由质量 | 有效 token | 耗时 |
|---|---:|---:|---:|---:|
| Pi 单代理 | 40/40 | 不适用 | 64,353 | 110.6 秒 |
| Pi 公司模式 | 40/40 | 19/25 | 330,767 | 319.6 秒 |
| Codex 单代理 | 40/40 | 不适用 | 72,205 | 240.1 秒 |

Pi 公司模式相对 Codex：有效 token 增加 358%，耗时增加 33%，当前规则下没有测得质量增益。

## 逐样本观察

跨栈 OAuth 安全方案中，Pi 公司模式派发 `project_analyst` 和 `security_auditor`，未派发预期的 `architect` 与 `test_engineer`。它消耗 182,990 个有效 token，Codex 消耗 45,417 个；两者内容质量均为 20/20。

并发重复导入诊断中，Pi 公司模式派发 `debugger` 和 `test_engineer`，未派发预期的 `architect`。它消耗 147,777 个有效 token，Codex 消耗 26,788 个；两者内容质量均为 20/20。

Pi 的并行派发有效降低了串行校准时的墙钟时间，但专家重复扫描仓库是主要 token 放大器。四次 subagent 运行合计执行 127 次工具调用，单个专家消耗约 47.7k–89.6k 有效 token。

## 判定与下一版门槛

当前版本不应默认对普通需求开发启用公司模式。默认应使用单代理，只在独立安全审计、复杂根因诊断、跨领域架构决策或最终验证需要隔离责任时升级到 subagent。

下一版优化应同时满足：

- 项目级配置模型、thinking、最大回合、最大工具调用和 token 预算。
- 父代理先生成一次共享项目事实包，专家只读取相关切片，禁止重复全仓扫描。
- 路由采用条件门禁，不按角色清单机械派发；未达到风险或复杂度阈值时保持单代理。
- 需求阶段的专家默认使用更低成本模型或更紧预算，高风险结论再升级模型。
- 扩展 A/B 到真实实现、测试编写、审查、安全审计与验证闭环，并采用盲评或更有区分度的质量规则。

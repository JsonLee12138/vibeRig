# Pi 开发阶段 A/B 证据

## 结论

在两个实现型 fixture 中，`dev_only` 是当前默认最优路径：Terra 与 MiMo-V2.5 都达到隐藏合同 14/14；MiMo 用时 92.3 秒、有效 token 20,742，分别比 Terra 少 16.7% 和 16.6%。

额外的 test、review、security、verify 没有提高任何一个 fixture 的隐藏准确率。Terra 完整流程仍为 14/14，但耗时达到纯开发的 6.71 倍、token 达到 6.42 倍，且 verifier 判定其中一个 security 变更违反规格。MiMo 完整流程耗时达到纯开发的 9.90 倍、token 达到 10.70 倍，security 还把准确率从 14/14 降到 7/14。

因此，默认路由应使用单 implementer；test 和 review 按风险触发；security 只能生成隔离候选补丁，禁止自动覆盖已通过合同的实现；verify 保留为只读发布门禁。

## 测试口径

- 分支：`codex/pi-company-plane`
- 模型：`openai-codex/gpt-5.6-terra` 与 `xiaomi-token-plan-cn/mimo-v2.5`
- 推理级别：均为 `low`
- fixture：租户隔离与幂等事件账本、OAuth 密钥加密与事务审计
- starter 隐藏基线：事件账本 2/7，OAuth 配置 1/7
- 隔离：关闭 Pi context files、extensions 与 skills；隐藏测试只在评分时临时复制，评分后立即删除
- 顺序：纯开发 → 测试员工与修复 → reviewer 与修复 → security 与修复 → 只读 verify
- 时间：累计串行 agent 墙钟时间，不包含隐藏评分时间
- 有效 token：`input + output + cacheWrite`，排除重复的缓存前缀读取
- 优先级：准确率 > 时间 > token

## 回退根因

MiMo 的事件账本 security 阶段把“重复请求返回原始记录”改成返回深拷贝，两个引用一致性合同失败。verifier 在风险说明中识别了偏差，但其 JSON 仍给出 `passed: true`，说明不能只消费布尔值，还要把风险转成候选变更门禁。

MiMo 的 OAuth security 阶段把 `keyVersion` 收紧为有限数字，而需求只要求持久化加密依赖的输出，测试依赖合法返回字符串 `kms-v7`。这导致所有正常保存路径提前抛出验证错误，隐藏准确率从 7/7 降到 2/7；公开测试仍通过，证明测试员工生成的用例不能代替项目所有者维护的验收合同。

Terra 的事件账本 security 阶段拒绝任何覆写 `has/get/set` 的 Map。隐藏测试未覆盖该场景，但 verifier 根据“state 只需是 Map”的合同判定为规格外拒绝，因此最终技术门禁失败。

## 路由建议

普通需求开发默认只运行 implementer，并允许项目配置首选模型。当前小样本中 MiMo-V2.5 的纯开发准确率与 Terra 相同，同时更快、更省 token，可进入真实项目 shadow 模式继续验证。

测试员工只在新增公共 API、复杂状态转换、回归修复或项目缺少相应验收覆盖时触发。reviewer 默认只读输出 finding，不直接改源码；需要整改时，在独立候选工作区应用后重新跑项目合同。

security 默认只读。确需整改时必须使用候选工作区，并依次通过原始测试、项目验收合同和独立 verifier；任何分数下降、`passed: false` 或未处置的合同风险都拒绝合并。verify 保持只读发布门禁，不承担修复职责。

机器可读结果见 `pi-development-ab-2026-07-28.json`。由于当前只有两个合成 fixture、每个模型单次采样，本结论用于选择下一轮默认策略，不视为统计显著的模型排行。
